# وصّلها — تطبيق Flutter (نسخة أصلية)

نسخة Flutter أصلية من تطبيق وصّلها، بتتصل بنفس مشروع Supabase اللي الموقع
(`../src`) بيستخدمه بالظبط — نفس الجداول، نفس الـ RPCs، نفس الـ Edge
Functions. مفيش أي تغيير في الباك إند.

## ليه Flutter بدل Capacitor؟

الموقع متغلّف بالفعل كتطبيق موبايل عبر Capacitor (WebView) — شغّال وجاهز
للنشر. النسخة دي بديل **أصلي حقيقي** (native) لأداء وسرعة أفضل، مش تعديل
على النسخة الحالية.

## 3 تطبيقات، كود واحد

بدل تطبيق واحد بيتغيّر حسب دور المستخدم بعد تسجيل الدخول، الكود مقسّم
لـ **3 نُسخ تثبيت منفصلة** (Flutter product flavors) — نفس كل الشاشات
والمنطق، بس كل نسخة عندها اسم وأيقونة و`applicationId` خاص بيها، فتقدر
تتنشر كتطبيقات منفصلة على المتجر:

| النسخة | لمين | الدخول لأول شاشة |
|---|---|---|
| `customer` | العملاء | `lib/main_customer.dart` |
| `driver`   | السائقين المعتمدين | `lib/main_driver.dart` |
| `merchant` | أصحاب المتاجر | `lib/main_merchant.dart` |

كل نسخة بترفض تسجيل الدخول لو دور الحساب (`accounts.role`) مايطابقش
النسخة دي — يعني سائق مايقدرش يدخل نسخة العملاء وبالعكس.

**الأدمن مالوش نسخة Flutter** — لوحة الأدمن الحالية على الموقع
(`admin.astro`) شاملة وجاهزة على الموبايل (متصفح)، مفيش داعي لتكرارها.

## الحالة الحالية

**جاهز وشغّال:**
- تسجيل الدخول (كل النسخ) + إنشاء حساب (نسخة العملاء بس — انضمام
  السائق/التاجر لسه عبر الموقع، ده تطبيق KYC مراجعة إدارية مش تسجيل فوري)
- **نسخة العملاء**: المشاوير (بحث عناوين، حساب الأجرة، تتبع لحظي)،
  المحفظة (رصيد/إيداع/سحب/تحويل)، واجهة رئيسية بـ 6 تبويبات
- **نسخة السائق**: تفعيل/إيقاف الاستقبال، عرض عرض جديد وقبوله أو رفضه،
  تحديث حالة الطلب (استلام/تسليم) أو إنهاء المشوار
- **نسخة التاجر**: قائمة الطلبات (جديدة/قيد التنفيذ/سجل) بتحديث لحظي،
  قبول/رفض الطلبات الجديدة

**قريباً (نفس النمط، جاهز للتوسعة):** توصيل الطرود، خدمة دليفري العامة،
تتبع موقع مستمر للسائق (حاليًا نقطة واحدة عند الاتصال، مش تتبع مباشر).

## التشغيل

```bash
flutter pub get

# كل نسخة محتاجة --flavor + -t لملف main المطابق:
flutter run --flavor customer -t lib/main_customer.dart
flutter run --flavor driver   -t lib/main_driver.dart
flutter run --flavor merchant -t lib/main_merchant.dart

# نسخة أندرويد جاهزة للتوزيع:
flutter build apk --flavor customer -t lib/main_customer.dart
flutter build apk --flavor driver   -t lib/main_driver.dart
flutter build apk --flavor merchant -t lib/main_merchant.dart
```

`flutter run` من غير `--flavor`/`-t` بيشغّل نسخة العملاء افتراضيًا
(`lib/main.dart`).

### iOS

إعداد الـ flavors لـ iOS محتاج خطوة يدوية إضافية داخل Xcode (إنشاء
Scheme لكل نسخة) — ده مش حاجة تتعمل بتعديل نصي آمن من غير Xcode نفسه،
ومحتاج جهاز ماك أصلاً. لو محتاج iOS، افتح `ios/Runner.xcworkspace` في
Xcode واعمل 3 Schemes (customer/driver/merchant) بنفس منطق الـ Android
flavors فوق — [توثيق Flutter الرسمي لخطوة iOS](https://docs.flutter.dev/deployment/flavors).

## البنية

```
lib/
  app.dart            # نقطة التشغيل المشتركة لكل النسخ + بوابة الجلسة/الدور
  core/               # اتصال Supabase، الجلسة، الأدوار (flavor.dart)، أدوات مشتركة
  main_customer.dart  # نقاط دخول رفيعة — كل واحدة بتنادي app.dart بإعداد النسخة بتاعتها
  main_driver.dart
  main_merchant.dart
  features/
    auth/             # تسجيل دخول / حساب جديد (مع فحص الدور لكل نسخة)
    home/             # واجهة العميل الرئيسية + شريط التنقل
    rides/            # المشاوير (نسخة العملاء)
    wallet/           # المحفظة (نسخة العملاء)
    driver/           # لوحة السائق
    merchant/         # لوحة التاجر
  shared/widgets/     # عناصر مشتركة (زر تسجيل الخروج، شاشة "قريباً")
```

كل ملف فيه تعليق بيوضّح مصدره المطابق في الموقع (مثلاً "ported 1:1 from
src/utils/phone.ts") — أي تعديل في القاعدة (الأجرة، قواعد الباسورد،
التحقق من الجوال) لازم يتزامن في المكانين.
